# 巨量引擎优化师绑定方案

本文约定投放团队如何把**巨量广告后台的广告主账户**绑定到优化师，以及之后如何换绑、解绑。方案按巨量广告后台的常见业务编写，管理的是团队内部的责任归属。

登录巨量后台、把协作者加进组织，仍按巨量广告后台现有的成员流程办理。账户以巨量后台可见的**广告主 ID** 为准，人员以本团队在职花名册为准。下文的字段是建议落库的业务字段，不是现成的内部接口。

## 1. 目标与范围

### 1.1 目标

任一时刻，每个在投广告主账户有且只有一名主优化师。绑定、换绑、解绑都留下申请单和操作记录。业绩按生效时刻切开：生效前归原责任人，生效后归新责任人。误操作可以在窗口内回滚，已锁定的历史归属保持不动。

### 1.2 纳入

| 动作 | 含义 |
| --- | --- |
| 绑定 | 为空缺账户指定主优化师，或为已有主责的账户增加协作优化师 |
| 换绑 | 更换主优化师，或替换其中一名协作优化师 |
| 解绑 | 解除某名协作；或解除主责。解除主责时必须指定继任，或明确进入待分配 |

界面上「解绑主责并指定继任」落成**换绑**，与换绑共用同一套生效步骤，避免两套切换逻辑。只有选择「进入待分配」时，单据类型才记为解绑。

### 1.3 不纳入

- 巨量侧开户、资质、充值、对公、发票
- 计划、创意、出价、素材等投放操作
- 腾讯广告、磁力引擎等其他媒体的账户
- 改写已经锁定日期的历史业绩
- 代替人工去暂停巨量后台里的在投计划

待分配超时只在内部账户列表上标出并通知管理员。要不要在巨量后台暂停投放，由管理员人工决定。

### 1.4 名词

| 名词 | 含义 |
| --- | --- |
| 广告主账户 | 巨量广告后台中的一个广告主，以广告主 ID 识别 |
| 主优化师 | 对该账户投放结果负责的人，同一时刻最多一名 |
| 协作优化师 | 可协助操作，不承担该账户主考核 |
| 待分配 | 在投账户当前没有生效中的主优化师 |
| 生效时刻 | 新旧责任切换的时间点，时区为 Asia/Shanghai |
| 业绩锁定 | 某个自然日的归属不再允许回滚。默认次日 12:00 锁定前一日 |

## 2. 角色与权限

角色只有三种：优化师、主管、管理员。一个人可以只有一个角色。主管看本团队，管理员看全部团队。

### 2.1 权限

| 能力 | 优化师 | 主管 | 管理员 |
| --- | --- | --- | --- |
| 查看自己的当前绑定和历史 | 允许 | 允许 | 允许 |
| 查看本团队账户与绑定 | — | 允许 | 允许 |
| 查看全部团队 | — | — | 允许 |
| 申请把自己加为协作 | 允许，账户已有主责且协作未满 | 允许 | 允许 |
| 申请接手空缺主责 | 允许，账户无主责且未超个人容量 | 允许 | 允许 |
| 代本团队成员发起绑定、换绑、解绑 | — | 允许 | 允许 |
| 审批本团队普通单据 | — | 允许，见下方回避规则 | 允许 |
| 审批跨团队、超容量、在投主责解绑、待分配超时后的补绑 | — | — | 允许 |
| 免审批直接办理 | — | — | 允许，原因必填，仍生成申请单 |
| 回滚最近一次生效 | — | — | 允许，须满足第 6 节窗口 |
| 修改容量、人数、超时、回滚窗口等配置 | — | — | 允许 |

「—」表示该角色没有这项能力。

### 2.2 审批回避

主管不能审批下面两类单，单据改由管理员审批：

- 新责任人或原责任人是主管本人
- 申请人是主管本人，且单据会改变主优化师

优化师没有审批权。管理员直接办理自己相关的账户时，必须填写原因，并在操作日志中保留办理人。

### 2.3 团队归属

账户当前归属团队等于当前主优化师所属团队。待分配账户沿用最近一名主优化师的团队。从未绑定过的账户，由管理员在第一次绑定申请里指定归属团队。

新优化师的团队与账户归属团队不一致时，视为跨团队，只有管理员能审批。

## 3. 绑定规则

### 3.1 一人多户

一名优化师可以同时负责多个广告主账户。

- 计入容量的，是「生效中的主责」且账户投放状态为在投的数量
- 协作不占主责名额
- 默认上限 30，管理员可按人调整
- 达到上限后仍可提交申请，审批人变为管理员，系统不直接拒绝

停投、封禁账户上残留的主责不占名额，但名单里要能看到，方便后续解绑。

### 3.2 一户多人

每个广告主账户：

- 主优化师：生效中恰好 1 名。待分配期间为 0 名
- 协作优化师：0 到 2 名，默认上限 2，管理员可配置
- 同一人不能同时是该账户的主责和协作
- 同一人不能在该账户占两个协作名额

在投账户进入待分配后，应在 1 个工作日内补上主优化师。第一期没有节假日数据源时，「1 个工作日」按进入待分配后 24 小时计算。超过时限后账户标记为「待分配超时」，并通知管理员。

已有主责时，再提交「绑定主责」直接拒绝，提示改走换绑。没有主责时，不能提交「绑定协作」。

换绑主责时，原主优化师在新生效时刻结束，不自动变成协作。如果仍需要原人协助，另提一张协作绑定申请。

### 3.3 冲突

同一广告主账户只要存在未完结申请（待审批、已通过待生效），就拒绝新申请。申请人可以撤回自己的待审批单后再提。管理员可以驳回未完结单后再办。

以下对象不能作为新的主责或协作：

- 已离职、已停用的人员
- 已经是该账户当前主责或当前协作的人员（换绑时的「新人」不能与「旧人」相同）

账户投放状态为封禁、注销或资质未通过时：

- 拒绝新绑定，也拒绝换入新的主责或协作
- 允许把现有主责解绑到待分配，允许解除现有协作

两条申请同时提交时，先成功写入的那条占住「未完结」位置，后一条提交失败并返回已存在的单号。

### 3.4 生效时间

时区固定为 Asia/Shanghai。

申请人选择期望生效日期，只能是今天，或今天起 7 个自然日内的某一天。默认是次日，避免把同一天的消耗拆给两个人。选择当天时，提交前要求二次确认，并在申请单上记下「申请人确认拆日」。

实际生效时刻：

- 审批通过时间早于期望生效日 00:00：在该日 00:00 生效
- 审批通过时间已经到了期望生效日或更晚：审批通过后立即生效。立即生效只切分当天剩余消耗，不回头改写审批时刻之前的消耗

已生效单据的生效时刻不能修改。要改责任人，重新走换绑或解绑。

业绩口径：消耗发生时间早于生效时刻的，归旧绑定；等于或晚于生效时刻的，归新绑定。按消耗发生时间切，不按报表拉取时间切。查询「某日责任人」时，用该日结束时刻（次日 00:00）之前最后一段覆盖该日的关系；若当天中途换绑，当天按生效时刻拆成两段，分别统计。

### 3.5 默认配置

管理员可改，改配置不影响已经生效的历史关系，只影响之后新提交的申请。

| 配置项 | 默认值 |
| --- | --- |
| 在投主责上限（每人） | 30 |
| 每户协作人数上限 | 2 |
| 审批超时 | 提交后 48 小时 |
| 期望生效日最远 | 今天起 7 个自然日 |
| 回滚窗口 | 生效后 24 小时，且该自然日尚未锁定 |
| 业绩锁定 | 次日 12:00 锁定前一自然日 |
| 待分配时限 | 进入待分配后 24 小时 |

## 4. 操作流程

### 4.1 申请

入口放在账户详情的「绑定管理」。主管也可以从团队账户列表发起。

必填：

- 动作：绑定、换绑、解绑
- 广告主 ID（带出账户名称，提交时再核对一次 ID 与名称是否仍匹配）
- 角色：主责或协作
- 人员：绑定填新责任人；换绑填原责任人和新责任人；解绑协作填要解除的人；解绑主责填「继任人」或「进入待分配」
- 期望生效日期
- 原因，至少 10 个字

提交后生成单号 `BD-YYYYMMDD-四位序号`，序号按日从 0001 递增。状态为待审批。待审批期间，申请人或同团队主管可以撤回，撤回后绑定关系不变。

管理员直接办理时同样生成申请单，状态写为已通过待生效，审批人记管理员本人，原因不能为空。若生效时刻不晚于办理时刻，随即进入生效。

提交时就做一次规则校验（在职、容量是否需升级审批人、人数、冲突、账户状态、未完结单据）。校验不通过则不生成申请单，并返回具体原因。

### 4.2 审批

审批路由：

| 条件 | 审批人 |
| --- | --- |
| 本团队、未超容量、无冲突、不触犯回避、不是「在投账户解绑主责进入待分配」 | 该团队主管 |
| 跨团队、超容量、回避、在投主责解绑进入待分配、待分配超时后的补绑 | 管理员 |

审批动作只有通过和驳回。驳回必须填写原因。通过后计算实际生效时刻，状态改为已通过待生效。

提交满 48 小时仍未审批：状态改为已过期，绑定关系不变，通知申请人。过期单不能恢复，需要重新申请。

驳回、撤回、过期都不改变当前绑定。

### 4.3 生效

到达生效时刻后执行生效。同一张申请单只生效一次，重复执行直接返回已生效结果。

对同一广告主 ID，生效和回滚串行处理。步骤放在同一事务里：

1. 锁住该广告主 ID
2. 按第 3 节再校验一次（人员仍在职、容量、人数、账户状态、没有另一张已到点的未完结单）
3. 结束应当结束的旧关系，结束时间等于生效时刻
4. 写入新关系，开始时间等于生效时刻，状态为生效中。解绑主责进入待分配时不写新主责
5. 重算账户当前快照：当前主责、当前协作列表、是否待分配、最近生效单号
6. 申请单改为已生效
7. 写入操作日志

任何一步失败，整笔事务撤销。旧关系保持原样，新关系不写入，申请单保持已通过待生效。

日切任务每分钟扫描「已通过待生效且计划生效时刻已到」的单据。审批当时就该立即生效的，在审批通过的同一次处理里直接生效，不等下一分钟。

### 4.4 通知

通知是站内消息。团队如果已经在用企业微信或邮件，可以同时抄送。发送失败不影响生效。

| 时机 | 接收人 |
| --- | --- |
| 提交成功 | 当前审批人 |
| 驳回、撤回、过期、生效前取消 | 申请人 |
| 审批通过 | 申请人、新责任人、原责任人、账户所属主管 |
| 生效 | 同上 |
| 回滚 | 同上，并包含办理回滚的管理员 |
| 待分配超时 | 管理员，以及账户所属主管 |

通知内容至少包括：单号、广告主 ID、账户名称、动作、角色、人员、生效时刻、原因摘要。

发送失败后 15 分钟内重试，最多 3 次。仍失败则记入待补发列表，管理员可以手动补发。补发只重发消息，不重新生效。

## 5. 数据字段与状态

### 5.1 申请单

| 字段 | 说明 |
| --- | --- |
| 单号 | `BD-YYYYMMDD-四位序号`，唯一 |
| 动作 | 绑定、换绑、解绑 |
| 广告主 ID、账户名称 | 提交时写入；生效前再核对名称 |
| 角色 | 主责、协作 |
| 原责任人 | 换绑、解绑时必填；纯绑定为空 |
| 新责任人 | 绑定、换绑时必填；解绑进入待分配时为空 |
| 进入待分配 | 是或否。仅解绑主责且无继任时为是 |
| 期望生效日期 | 日期 |
| 计划生效时刻 | 审批通过时写入 |
| 实际生效时刻 | 生效成功时写入 |
| 确认拆日 | 期望日期为当天时为是 |
| 原因 | 申请原因 |
| 驳回原因、取消原因、回滚原因 | 按动作填写 |
| 状态 | 见 5.3 |
| 申请人、申请时间 | |
| 审批人、审批时间 | 直接办理时审批人等于办理人 |
| 所属团队 | 提交时的账户归属团队 |

### 5.2 绑定关系

一条关系表示「某人在一段时间内以某种角色负责某账户」。结束和回滚都不删除记录。

| 字段 | 说明 |
| --- | --- |
| 关系编号 | 唯一 |
| 广告主 ID | |
| 人员 | 优化师 |
| 角色 | 主责、协作 |
| 状态 | 生效中、已结束、已回滚 |
| 开始时间、结束时间 | 结束时间为空表示仍在生效。已回滚的关系保留原时间段，供审计 |
| 来源单号 | 产生这条关系的申请单 |
| 结束单号 | 结束或回滚这条关系的申请单，可空 |

账户当前快照是冗余，方便列表查询。字段包括：广告主 ID、账户名称、投放状态、归属团队、当前主责、当前协作列表、待分配标记、进入待分配时间、最近生效单号、快照更新时间。快照与关系不一致时，以绑定关系重算快照。

当前主责的判定：该广告主 ID 下，角色为主责、状态为生效中、开始时间不晚于当前时间、结束时间为空的那一条。正常情况下最多一条。出现多条时列表展示「数据异常」，并禁止继续提交新申请，直到管理员按操作日志修到只剩一条。修复采用回滚或补一条结束记录，不物理删除。

某时刻的责任人：开始时间不晚于该时刻，且（结束时间为空或结束时间晚于该时刻），状态为生效中或已结束。已回滚的关系不参与归属计算。

### 5.3 申请单状态

```text
待审批 --通过--> 已通过待生效 --到点生效成功--> 已生效
   |                    |
   |--驳回--> 已驳回     |--生效前校验失败并取消--> 已取消
   |--撤回--> 已撤回     |--管理员回滚----------> 已回滚
   |--超时--> 已过期
```

| 状态 | 含义 | 当前绑定 |
| --- | --- | --- |
| 待审批 | 等待审批 | 不变 |
| 已驳回 | 审批人驳回，终态 | 不变 |
| 已撤回 | 申请人或主管撤回，终态 | 不变 |
| 已过期 | 48 小时未审批，终态 | 不变 |
| 已通过待生效 | 已批准，未到生效时刻或生效尚未成功 | 不变 |
| 已取消 | 生效前因离职、封禁等原因取消，终态 | 不变 |
| 已生效 | 切换已写入 | 已切换 |
| 已回滚 | 本次生效被管理员撤销 | 恢复到上一份生效快照 |

绑定关系只有三种状态：生效中、已结束、已回滚。

### 5.4 操作日志

每次提交、撤回、通过、驳回、过期、取消、生效、生效失败、回滚、补发通知、修改配置，都记一条日志。字段：时间、操作者、对象类型（申请单、绑定关系、配置）、对象编号、动作、变更前后摘要、原因。日志只追加，不修改、不删除。

## 6. 异常与回滚

### 6.1 异常处理

| 场景 | 处理 | 绑定结果 |
| --- | --- | --- |
| 审批超过 48 小时 | 申请单改为已过期，通知申请人 | 不变，需重新申请 |
| 生效前人员离职或停用 | 申请单改为已取消，写明原因，通知申请人与主管 | 不变 |
| 生效前账户变为封禁、注销、资质未通过 | 取消尚未生效的换入、新绑定；已经是解绑到待分配的单据可以继续生效 | 按取消或继续生效的结果 |
| 生效事务失败 | 事务全部撤销，申请单保持已通过待生效，通知管理员 | 旧关系仍在，新关系未写入 |
| 同一单重复生效 | 第二次直接返回已生效结果 | 不产生第二套关系 |
| 同一账户并发两张新单 | 后提交的一张失败，并返回先占用的单号 | 只保留先成功的未完结单 |
| 生效后发现主责关系多于一条 | 账户标记数据异常，暂停接受新申请 | 不自动猜测删哪一条 |
| 待分配超过 24 小时 | 标记待分配超时，通知主管和管理员 | 保持无主责，直到新的绑定生效 |
| 通知失败 | 进入待补发，15 分钟重试，最多 3 次 | 生效结果不回退 |
| 离职人员名下仍有生效主责 | 账户列表标记待换绑，通知主管 | 关系先保持，由主管发起换绑或解绑 |

生效失败后每 10 分钟自动重试，连续失败 6 次停止自动重试，转人工处理。人工处理完成后，由管理员对原单触发再次生效，不另开一张单，保证单号幂等。

### 6.2 回滚

只有管理员可以回滚。同时满足以下条件才允许：

- 对象是该账户最近一次已生效的绑定、换绑或解绑
- 距离实际生效时刻不满 24 小时
- 生效时刻所在自然日尚未锁定（默认次日 12:00 之前）
- 该账户没有另一张待审批或已通过待生效的申请。有的话先撤回、驳回或等它完结

回滚立即生效，步骤同样放在一个事务里：

1. 锁住该广告主 ID
2. 把这次生效新写入的关系标为已回滚
3. 把这次生效所结束的关系恢复为生效中，清空结束时间和结束单号
4. 按关系重算账户快照
5. 原申请单改为已回滚，记下回滚原因和操作者
6. 写操作日志，并发送通知

回滚不删除申请单和关系记录。超过回滚窗口，或该日业绩已锁定，则拒绝回滚。纠偏方式是再提一张换绑，原因里写明纠偏区间。已锁定日期的归属不再改写。

### 6.3 操作示例

**新户绑定。** 账户无主责。主管为团队内优化师甲发起绑定主责，期望生效日为次日。审批通过后，次日 00:00 之前账户仍无主责；00:00 生效后主责为甲。

**离职换绑。** 主责乙即将离职。主管发起换绑，新主责为丙，期望生效日为离职当日。审批在前一日通过，则离职当日 00:00 切换。乙在该日 00:00 之前的消耗归乙，之后归丙。

**误绑回滚。** 管理员当天把主责错办成丁，生效未满 24 小时且当日未锁定。回滚后当前主责回到上一任，丁的那条关系状态为已回滚，申请单状态为已回滚。

**窗口外纠偏。** 错误绑定已过次日 12:00。不再回滚。主管发起新的换绑，从新的生效时刻起改归新人，原因注明此前某日的归属保持不动。

## 7. 验收标准

下列条目都通过，才算这套绑定可用。

### 7.1 权限

1. 优化师只能看到自己的绑定，看不到其他团队账户。
2. 主管能看到本团队账户，不能审批跨团队单据。
3. 优化师不能审批任何单据。主管不能审批自己作为新主责或原主责的换绑，该单进入管理员待办。
4. 管理员直接办理时仍生成申请单，原因为空则不能提交，操作日志能查到办理人。

### 7.2 规则

5. 在投且无主责的账户可以绑定主责。已有主责时再绑定主责被拒绝，并提示改走换绑。
6. 无主责时不能绑定协作。协作已达 2 人时，再增加协作被拒绝。
7. 同一人不能同时成为同一账户的主责和协作。
8. 一名优化师的在投主责达到 30 后，新的主责申请仍能提交，但主管不能审批，只能由管理员审批。
9. 同一账户已有待审批或已通过待生效的单据时，第二张申请提交失败，并带出已有单号。撤回第一张后可以再提。
10. 离职人员不能被选为新责任人。封禁、注销、资质未通过的账户不能换入新人，可以解绑主责进入待分配。

### 7.3 流程与生效

11. 主管发起绑定主责且期望生效日为次日。审批通过后，次日 00:00 前当前主责仍为空；00:00 之后主责为该优化师，申请单为已生效。
12. 期望生效日选当天时，未做二次确认不能提交。审批通过后立即生效，审批时刻之前的消耗仍归原责任人。
13. 提交满 48 小时未审批，申请单变为已过期，当前绑定不变。
14. 驳回必须填写原因。驳回、撤回、过期后绑定关系与驳回前一致。
15. 解绑主责并指定继任的单据，生效结果与换绑一致：旧主责结束，新主责开始，中间不出现待分配。
16. 解绑主责并进入待分配后，账户带待分配标记。满 24 小时仍无主责时标记为待分配超时，主管和管理员能收到通知。

### 7.4 数据与业绩

17. 生效事务中途失败时，旧主责仍在，新主责不存在，申请单仍为已通过待生效。
18. 同一申请单连续触发两次生效，关系表里只有一套开始时间等于该生效时刻的新关系。
19. 消耗发生时间早于生效时刻的归旧优化师，等于或晚于生效时刻的归新优化师。同一自然日中途换绑时，当天能按时刻拆成两段。
20. 已结束、已回滚的记录仍可查询。当前主责查询不把已回滚关系算进去。
21. 账户快照与关系不一致时，按关系重算后，当前主责、协作列表、待分配标记与关系表一致。

### 7.5 回滚与通知

22. 生效后 24 小时内、且该日未锁定时，管理员回滚成功：当前主责恢复为上一任，本次新关系状态为已回滚，申请单状态为已回滚，记录仍在。
23. 超过 24 小时，或该日已过次日 12:00，回滚被拒绝。
24. 存在另一张未完结申请时，回滚被拒绝。
25. 通知发送失败时，绑定仍然生效，待补发列表能看到该条，手动补发不会第二次切换责任人。

## 8. 落地顺序

按下面的顺序做，前一步验收通过再做下一步。

1. 主责的绑定、换绑、解绑，加上申请、审批、到点生效和操作日志
2. 容量、人数、未完结冲突、账户状态、审批回避
3. 站内通知和待补发
4. 协作优化师
5. 回滚、待分配超时标记、业绩按生效时刻拆分的查询口径

第 1 步就可以在内部使用，第 5 步完成后按第 7 节全部条目验收。
